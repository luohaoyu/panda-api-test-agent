# 需求验收报告信息架构 v2.0

> **职责让渡声明（2026-11-01，已执行完毕）**：需求级验收报告的**唯一权威实现**是 `panda-api-test-agent-v2/scripts/render_requirement_report.py`（契约 `requirement-report.json`，规范见该技能 `references/requirement-report-spec.md`）。原兼容入口 `scripts/render_acceptance_report.py` 已于 2026-11-01 删除（备份见测试工作区 backup），任何场景下需求级报告一律走主 Agent 渲染器；本规范保留作为信息架构与人工登记（overlay）的语义参考，不再定义独立生成器。

## 0. 变更摘要（v1.1 → v2.0）

v1.1 的问题是「先有六层，再指望读者自己组装结论」。v2.0 反过来：**先定义读者必须拿到的五句话，再决定哪些层来支撑它**。

| # | v1.1 的问题 | v2.0 的改动 |
| --- | --- | --- |
| 1 | 名为跨运行聚合，实际只取最后一次运行 | 新增 **E1 结论演化**，记录每次运行的结论与翻转事件 |
| 2 | 五态与「三类清单」是两个维度，硬塞一层 | AC 状态扩为 **6 态**，清单由状态**派生**且互斥 |
| 3 | 「L2 证据齐但结论未定」无位置，只能降级或硬判通过 | 新增 `accepted_with_confirmation`（需确认，L2） |
| 4 | L1 结构把矩阵放在清单前，与 5 秒阅读路径冲突 | **清单前置、矩阵后置**，矩阵超 24 格折叠 |
| 5 | L3 装四类内容，用例明细把审计信息压到页底 | 拆 **L3a 运行事实（常显）/ L3b 用例明细（折叠）** |
| 6 | 无首屏契约、无规模策略 | 新增 **F0 首屏五问** 与规模/打印/窄屏约束 |

v1.1 原文见 `archive/acceptance-report-spec-v1.1.md`。

## 1. 定位与首屏契约

验收报告是**结论层**，唯一职责是让读者在无需滚屏的情况下回答五个问题。这不是摘要区，而是**主叙事**：L0–L5 从「章节」降级为「支撑」。

### F0 五问五答（首屏，必须在一屏内读完）

| 问 | 必须回答 | 判据来源 | 空态 / 禁止 |
| --- | --- | --- | --- |
| **Q1 能不能验收** | 三态结论：可验收 / 不可验收（缺证据）/ 不可验收（有缺陷） | 6 态计数 + `failed` 是否为 `product_defect` | 无运行证据时只能是「未验证」。禁止只写「通过/未通过」 |
| **Q2 谁该修** | 归因分布：产品缺陷 n / 环境 n（是否已解除）/ 测试自身 n（是否已修） | `failed` 分类 + 阻断归因 + 已翻转事件 | 无归因时写「无归因，无法分派」。禁止留空 |
| **Q3 我下一步做什么** | **≤3 条动作**，每条带 owner 与产出 | overlay 处置登记 | 无待办时写「无需动作，可进入评审」 |
| **Q4 结论可信吗** | 证据等级上限 + 非阻塞偏差是否全部公开 | 等级分布 + `required=false` 失败项计数 | 禁止只给通过率。必须显式写出「藏了什么」=0 |
| **Q5 你动了什么** | 写入对象数 / 清理状态 / 残留数 / 清除方式 | `cleanup` + `pending_objects` | 无写入时写「本次只读」。禁止把残留说成已清理 |

硬约束：

- **每个答案后必须挂锚点**，可一键跳到支撑区块；没有锚点的答案视为无证据结论，不得出报。
- F0 属判断层，页头标注「机器起草，未经人工确认」，不得表述为放行授权。
- F0 只放**结论句**，不放表格、不放指标卡堆叠。

## 2. 页面骨架（顺序即阅读优先级）

```text
[sticky 顶栏]  需求名 · verdict · 证据等级上限 · 版本条（常驻，任何滚动位置可见）

F0  五问五答                    ← 首屏，1 屏内
L1  处置清单（必须修/需确认/可接受残留）  ← 先看差在哪
L1  验收矩阵（AC 平面图）          ← 后看全景，>24 格折叠
E1  结论演化（跨运行时间线 + 翻转记录）
L2  需求覆盖树（AC→规则→场景→用例，默认折叠）
L3a 运行事实（门禁/清理/时间线，常显）
L3b 用例明细（默认折叠）
L4  边界与残留（缺口分级 + 残留清单 + 交接）
L5  证据索引与版本（变更记录）
```

## 3. AC 状态模型 v2（6 态）

判定按优先级从上到下命中即停：

| 优先级 | 状态 | 判定条件 | 最低等级 | 进入清单 |
| --- | --- | --- | --- | --- |
| 1 | `out_of_scope` | 需求上下文显式排除，写明理由与责任人 | — | 可接受残留 |
| 2 | `blocked` | 因门禁/凭据/环境/依赖未发请求，或执行 `error`，且有阻断归因 | L0 | 需确认（待解除） |
| 3 | `failed` | 必需用例 `failed` 且分类 `product_defect` | L2 | 必须修 |
| 4 | `accepted_with_confirmation` | 必需用例全 `passed`，但该 AC 下存在 `required=false` 断言 `failed` | L2 | 需确认 |
| 5 | `accepted` | 必需用例全 `passed`，且**无任何** `required=false` 断言 `failed` | L2 | 不进清单 |
| 6 | `not_verified` | 无用例覆盖，或从未执行且无阻断归因 | L0/L1 | 需确认 |

两条铁律：

- **清单由状态派生，一条 AC 只进一个清单**（互斥）。禁止人工把 `accepted` 的 AC 塞进「需确认」——那说明状态判错了，应改判 `accepted_with_confirmation`。
- **`required=false` 的失败不得被吞**。这是 v1.1 最危险的漏洞：机械套模型会把「脱敏口径与 PRD 不符」判成 `accepted`，正是 §5 禁止的「只给一个通过率让人以为整体已验收」。
- **失败断言按业务规则归属，不按用例覆盖范围扩散**。一条用例可覆盖多个 AC（实测 TC-007 同时挂 AC-001/007/010/013），若按用例归属，一个脱敏观察项会污染 4 个 AC。归属规则：`assertion.business_rule_refs ∩ AC.business_rule_refs ≠ ∅`；无规则引用的断言不得自动归属，须交 overlay 显式登记。

## 4. 等级与组合矩阵

| 状态 | 允许等级 | 说明 |
| --- | --- | --- |
| `accepted` / `accepted_with_confirmation` / `failed` | L2 / L3 / L4 | 低于 L2 不得判这三态 |
| `blocked` | **仅 L0** | 不允许「L2 的阻断」 |
| `not_verified` | L0 / L1 / L2 | **v2.0 放开 L2**：有 L2 证据但结论未闭合时，保留已获等级，不得降级抹掉证据 |
| `out_of_scope` | 不标等级 | 标注排除依据 |

等级含义不变（L0 未验证 / L1 静态 / L2 运行事实 / L3 状态事实 / L4 业务验收）。补充：**L1 可以支撑「字段存在性、契约一致性」类 AC**，但必须在该 AC 行标注 `L1-static`，不得与 L2 混算验收通过率。

## 5. 度量口径（三比率，分母写在数字旁）

| 指标 | 分子 / 分母 | 回答 |
| --- | --- | --- |
| 设计覆盖率 | 有业务规则引用的 AC / AC 总数 | 测了该测的吗 |
| 执行覆盖率 | 实际执行用例 / 计划用例 | 真的跑了吗 |
| 验收通过率 | `accepted` / AC 总数 | 能不能放行 |

`executed=0` 显示「不计算」。门禁数、接口数、用例数不得混入验收通过率分母。`accepted_with_confirmation` 既不进分子也不进分母修正，单独计数展示。

## 6. E1 结论演化（v2.0 新增）

**这是 v1.1 最大的功能缺失：报告只呈现最终快照，读者看不到结论如何成立、被什么推翻。**

数据契约（`evolution[]`，按时间正序）：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `run_id` | 是 | 运行标识 |
| `verdict` | 是 | 该轮结论 |
| `fact` | 是 | 一句话事实（含关键数字/状态码） |
| `no_new_info` | 否 | 与上一轮失败签名相同则标 `true`，显式记「无信息增量」 |
| `overturns` | 否 | 被本轮推翻的既往结论 id |
| `overturned_by` | 否 | 本结论后被哪轮推翻 |
| `report` | 否 | 该轮是否有可读报告；`false` 时写原因 |

渲染要求：

- 时间线逐轮成行，翻转事件用连接线标注「A 被 B 推翻」。
- **同一凭据、同一失败签名的重复运行必须显式标 `no_new_info`**，不得伪装成进展。
- 最终结论必须能回溯到支撑它的那一轮，且注明此前有多少轮被否决。

## 7. 布局约束

- **首屏**：1440×900 下 F0 五问必须完整可见；顶栏 sticky，滚到 L3b 第 40 条时仍能看到需求名、verdict、版本条。
- **规模**：矩阵 ≤24 格平铺；>24 格默认折叠并按状态分组，标题显示「N 格 · 需确认 n / 已验 n」。
- **折叠层级**：L2、L3b 默认折叠；L3a 常显。折叠用原生 `details`，不依赖脚本。
- **状态表达**：颜色 + 文字 + 等级角标三重，禁止仅用颜色；打印时角标保留。
- **打印**：L4/L5 单独成页，F0 单独成页，不跨页断开矩阵行。
- **窄屏**：矩阵退化为列表，禁横向滚动；F0 卡片单列。

## 8. 数据契约

输入（缺一不可，除非标注可缺）：

| 输入 | 用途 | 可缺省 |
| --- | --- | --- |
| requirement context（AC 清单、PRD 版本、基线 commit） | F0-Q1 计数、矩阵骨架 | 否 |
| TestPackage | L2 覆盖树、L3b 接口与用例 | 否 |
| 运行清单（N × `result.json` / `host-outcome.json` / `evidence/`） | L1/E1/L3、度量 | 是（则全 AC `not_verified`） |
| `overlay.json`（人工登记：owner、动作、确认理由、归因） | F0-Q3、清单处置、L4 交接 | 否（判断层需要 owner） |

`overlay.json` 约束（v2.0 新增，解决「确定性生成」与「人工登记」冲突）：

- 机器生成内容与人工登记内容**分区渲染**，人工字段一律带「人工登记」标记与登记人。
- 人工登记**不得覆盖**：状态判定的机器结果、数字、等级、生成时间、版本号。
- 人工可写：owner、动作、确认理由、责任归属、交接条件。
- 人工写了与机器判定冲突的处置（例如给 `accepted` 挂「需确认」），**渲染必须报错**，而不是静默采纳。

## 9. 生成器与校验

- 需求级报告由主 Agent 技能的 `render_requirement_report.py` 从 `requirement-report.json` 确定性生成；禁止手工拼 HTML，本技能不设独立生成器。
- 生成器必须内置并打印校验结果（失败则不出报）：

| # | 校验项 |
| --- | --- |
| 1 | AC 无漏项：`requirement_trace` 覆盖 package 全部 AC |
| 2 | 状态与等级组合合法（§4 矩阵） |
| 3 | 三比率可由原始计数重算一致 |
| 4 | `accepted` / `accepted_with_confirmation` 引用的证据文件必须真实存在 |
| 5 | `blocked` 必带缺口 id 与解除条件 |
| 6 | 每条 AC 都有 owner；每条动作都有产出物 |

- 报告不设签收区；版本号与生成时间由脚本写入，人工修改只追加变更记录行。
