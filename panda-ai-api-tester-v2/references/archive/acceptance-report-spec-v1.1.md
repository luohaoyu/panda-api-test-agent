# 需求验收报告信息架构

## 1. 定位

需求验收报告是**结论层**文档，回答三个问题：

1. 这个需求现在能不能验收？
2. 不能的话，差在哪、缺什么、谁来补？
3. 凭什么这么说——每个判断能否点回事实？

它不替代单次运行报告（`report-spec.md`）：运行报告是**事实子页**，一次运行一份，机器生成不可编辑；验收报告跨多次运行聚合，引用运行报告作为证据，并按需求维度给出结论。

```text
需求上下文(AC01..AC19) + TestPackage + N × (host-outcome / result / evidence)
                          ↓
                  需求验收报告（结论层）
                          ↓ 引用
                 单次运行报告（事实子页，1..N）
```

## 2. 三层分离（铁律）

| 层 | 区块 | 归属 | 可编辑性 |
| --- | --- | --- | --- |
| 判断层 | L0 结论带、L1 验收矩阵 | 机器起草 | 结论文字由模板起草，页头标注「未经人工确认」；不得表述为放行授权 |
| 事实层 | L2 需求覆盖树、L3 运行事实 | 机器生成 | 不可编辑；要改必须重跑 |
| 追溯层 | L4 风险与边界、L5 附录与版本 | 机器汇总 + 人工登记 | 只增不改，需记录登记人 |

两条硬约束：

- 事实层不得出现判断形容词（"基本可用""大概率""应该没问题"）。
- 判断层的每个结论必须能点回事实层锚点，否则视为无证据结论，不得出报。

报告本身**不设签收区**。签收属于评审流程的动作，由评审会、工单或审批系统留痕；报告只负责让「哪个版本的结论对应哪份证据」可追溯（版本号 + 生成时间 + 变更记录），不承担批准记录。评审通过后在报告外引用报告 URL 或版本号即可。

## 3. 结构契约

| 区块 | 回答的问题 | 必须包含 | 数据来源 | 空态 | 禁止 |
| --- | --- | --- | --- | --- | --- |
| **L0 结论带** | 能不能验收 | 一句话结论；AC 总数 / 已验收 / 未验证 / 阻断 四项计数；约束标签（环境、模式、证据等级）；版本条（PRD 版本 + 基线 commit、画像 revision、配置 revision、包 ID、运行 ID、生成时间） | requirement context、package、运行清单 | 无运行证据时结论只能是「未验证」 | 出现"通过/未通过"字样；把门禁数混入用例数 |
| **L1 验收矩阵** | 差在哪 | AC 平面图（每格：AC 编号 + 状态 + 证据等级角标）；三类清单：必须修 / 需确认 / 可接受残留；一句话「为什么是这个结论」 | L2 汇总 + 缺口登记 | 有阻断归因时全格 `blocked`，无归因时全格 `not_verified`；清单区显示阻断原因 | 用颜色单独表意；隐藏未覆盖格 |
| **L2 需求覆盖树** | 每个 AC 谁证明 | AC → 业务规则 → 场景 → 用例 → 断言 的逐级状态与证据引用；未覆盖 / 未执行显式成行 | package 的 requirements / business_rules / scenarios / cases + result 的 requirement_trace | 未覆盖记 `uncovered`，不得留空 | 上级 passed 而下属全未执行 |
| **L3 运行事实** | 请求与断言发生了什么 | 接口清单（契约、画像生命周期、是否被触达）；门禁事实（非生产、认证 verified/declared_only、清理能力）；用例明细（预期/实际/断言/分类/证据）；执行时间线（包校验→门禁→夹具→用例→清理→verdict） | result.json、evidence/、host-outcome.json | 显示 `executed=0` 与阻断阶段、耗时 | 把未发送请求的用例计为失败 |
| **L4 风险与边界** | 什么没验证、谁负责 | 缺口分级（blocking / 非阻断 / 参考）；证据边界声明（"本次只能得出 HTTP 层事实，不能得出落库结论"）；清理与残留；凭据与数据安全声明；外部依赖交接（缺什么、谁给、给了怎么跑） | known_gaps、cleanup、host-outcome、交接单 | 无缺口时显示"无登记缺口"，不得省略区块 | 用"未发现"代替"未验证" |
| **L5 附录与版本** | 数字从哪来 | 证据索引（可点开的 evidence 文件）；运行清单（每次运行的 ID / 模式 / verdict / 时间）；口径与算法说明（通过率、状态机、证据等级）；版本信息（报告版本、生成时间、数据来源、架构版本）；变更记录 | 运行目录、规范版本 | 无变更时仅保留首行生成记录 | 手工改数字而不改来源；在报告内设置签收表 |

## 4. AC 状态模型

每格 AC 只有 5 种状态之一，且必须与证据等级匹配：

| 状态 | 含义 | 最低证据等级 | 触发条件 |
| --- | --- | --- | --- |
| `accepted` | 验收通过 | L2 | 覆盖该 AC 的全部必需用例 `passed`，且断言级证据齐全 |
| `failed` | 验收不通过 | L2 | 有必需用例 `failed`，且分类为 `product_defect` |
| `blocked` | 无法判定（外部阻断） | L0 | 因门禁/凭据/环境/依赖未发送请求，或执行 `error` |
| `not_verified` | 未验证（无证据） | L0 / L1 | 无用例覆盖，或用例存在但从未执行且无阻断归因 |
| `out_of_scope` | 本期不验 | — | 在需求上下文显式排除，且写明理由与责任人 |

状态与等级的合法组合：

```text
accepted / failed      → 必须 L2 及以上
blocked                → 只能 L0（不允许 L2 的"阻断"）
not_verified           → L0 或 L1
out_of_scope           → 不标等级，标注排除依据
```

出现 `accepted` + L1、或 `blocked` + L3 这类组合，报告校验必须失败。

## 5. 证据等级

| 等级 | 名称 | 依据 | 可支撑的结论上限 |
| --- | --- | --- | --- |
| L0 | 未验证 | 无运行证据 | 不可下结论 |
| L1 | 静态证据 | 代码、契约、PRD 一致 | 接口存在、字段来源可追溯 |
| L2 | 运行事实 | HTTP 交换 + 结构化断言 | 接口行为符合契约 |
| L3 | 状态事实 | 库 / MQ / 轨迹只读观察 | 确实落库、异步收敛 |
| L4 | 业务验收 | 端到端场景 + 清理通过 | 业务结果正确、可交付 |

规则：

- 等级**只能由新运行提升**，不能靠解读既有证据"推断升级"。
- L2 不得写成 L3 结论：HTTP 200 不等于落库、不等于轨迹可见。
- 报告每个 AC 行必须带等级角标，缺失即校验失败。

## 6. 度量口径

三个比率各自独立，分母必须写在数字旁：

| 指标 | 分子 / 分母 | 用途 |
| --- | --- | --- |
| 设计覆盖率 | 有业务规则引用的 AC / AC 总数 | 证明"测了该测的" |
| 执行覆盖率 | 实际执行用例 / 计划用例（`skipped`、`not_run` 不进分子，仍进分母） | 证明"真的跑了" |
| 验收通过率 | `accepted` AC / AC 总数 | 回答"能不能验收" |

禁止事项：

- 禁止只给一个"通过率"，让读者误以为整体已验收。
- `executed=0` 时显示"不计算"，禁止 0% 或 100%。
- 门禁数量、接口数量不得混入用例通过率的分母。

## 7. 阅读路径

| 路径 | 读者 | 锚点顺序 | 目标时长 |
| --- | --- | --- | --- |
| 结论 | 决策者 | L0 结论带 → L1 三类清单 | 5 秒 |
| 定位 | 产品 / 业务 | L0 → L1 矩阵 → L2 未覆盖项 | 3 分钟 |
| 深挖 | QA / 研发 | L1 单格 → L2 规则 → L3 用例 → L5 证据文件 | 按需 |
| 审计 | 安全 / 流程 | L4 证据边界 → 缺口 → 凭据与清理声明 → L5 版本与变更记录 | 按需 |

导航要求：L1 每格可跳到 L2 对应行；L2 每行可跳到 L3 用例或 evidence；跳转必须是页内锚点或相对路径，离线可读。

## 8. 数据契约

输入（缺一不可，除非标注可缺）：

| 输入 | 用途 | 可缺省 |
| --- | --- | --- |
| requirement context（AC 清单、版本、基线） | L0 版本条、L1 矩阵骨架 | 否 |
| TestPackage | L2 覆盖树、L3 接口清单 | 否 |
| 运行清单与 `host-outcome.json` | L0 计数、L3 时间线、L4 阻断归因 | 是（则全 AC `not_verified`） |
| `result.json` | L2/L3 状态与断言、度量计算 | 是 |
| `evidence/` | L5 索引、断言溯源 | 否（有 result 时必须存在） |

**关键要求**：阻断型运行（无 `result.json`、0 次请求）必须仍能生成完整报告——L1 全格取 `blocked`（有阻断归因时）或 `not_verified`（无归因时），L0 结论写明阻断阶段与耗时，L4 列出解除条件。这正是当前 p943_4559 的真实处境，也是这套架构必须首先扛住的场景。

**推定规则（原型 v1.0 澄清）**：AC 状态取决于「覆盖用例是否执行」+「是否存在阻断归因」，与有无 `result.json` 无关。有归因 → `blocked`（L0）；无归因 → `not_verified`（L0/L1）。不得因为整次运行被阻断就把所有 AC 一律记成 `not_verified`——那会丢掉「谁该修」这条信息。

禁止：

- 引用其他项目或其他需求的运行结果作为本期证据。
- 用 `result.json` 缺失来省略 L1/L2 区块，让报告"看起来干净"。

## 9. 版式与可读性

沿用 `report-spec.md` 的视觉纪律，并补充：

- 状态一律「色 + 文字 + 等级角标」三重表达。
- 矩阵格在窄屏下退化为列表，不得横向滚动。
- 判断层与事实层用视觉分区（分隔线 + 层级色带），读者一眼能分辨哪句是判断。
- 必须支持打印：附录单独成页，证据索引可折叠。
- 不依赖 CDN、远程字体或前端脚本。

## 10. 生成器约束

- 验收报告由脚本从第 8 节输入确定性生成，禁止手工拼接 HTML。
- 判断层文字允许模板化起草；**版本号与生成时间为脚本写入的独立字段，不得由人工覆盖**，人工修改只追加变更记录行。
- 不得生成签收表、签字栏或任何形式的批准记录字段。
- 数字与结论必须双向可校验：任一结论行能反查到来源运行；任一数字能被重新计算验证。
- 新增 `validate_acceptance.py`，至少校验：AC 无漏项、状态与等级组合合法、三个比率与分子分母自洽、`accepted` 必引用存在的证据文件、`blocked` 必带缺口 ID 与解除条件。
