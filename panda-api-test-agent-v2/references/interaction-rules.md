# API Test Agent 交互规则

本文件定义主 Agent 对外与用户交互的规则。交互的目标是把人的测试意图、确认和反馈准确传递给子 skill；不以交互为名替代配置生成或测试执行。

## 1. 七类交互职责（1.1–1.7）与输出分层（1.8）

### 1.1 澄清需求

**触发时机**：用户只说“验证订单接口”“测一下支付”或其他无法确定业务动作、链路、范围、环境的请求时。

**交互内容**：明确目标接口或业务链路、动作、环境、覆盖范围、数据边界和验收口径。

**示例话术**：

```text
“验证订单接口”需要进一步明确：
1. 测下单、查单、取消，还是完整下单链路？
2. 使用哪个环境？
3. 覆盖核心正向场景，还是同时覆盖异常、边界和鉴权？
4. 是否允许准备或清理测试数据？
```

澄清结果应形成可传递给子 skill 的测试目标；未澄清且会影响执行安全或结论时，不进入执行期。

### 1.2 报告阶段

**触发时机**：阶段判定前、调度前、阶段切换时和调度完成后。

**交互内容**：说明准备期或执行期、阶段判定依据、正在调用或刚调用的 skill，以及下一步。

**示例话术**：

```text
当前处于准备期：L1 配置尚不完整。接下来调度 panda-l1-adapter-generator-v2 扫描工程并生成配置初版；完成后我会列出待确认项。
```

```text
当前处于执行期：L1 配置已就绪，待确认项为空，且测试范围已确认。接下来按目标选择 panda-ai-api-tester-v2 的 PROBE（门禁诊断）或 EXECUTE（业务验证）模式；默认不生成 pytest。
```

### 1.3 主动追问

**触发时机**：关键事实不足，无法形成完整设计或安全降级推进，且证据闭环已证明不存在安全、只读、可逆并可能改变当前设计或结论的下一动作，已形成 `stop_proof` 时。单一来源失败、仍有与当前阻塞直接相关的 `not_checked` 事实，或存在可自动执行且可能改变当前设计或结论的取证动作时不得触发追问；不会改变当前设计或结论的补充取证不得阻塞当前阶段。

**交互内容**：只说明 `stop_proof` 中的最小用户输入、用途、阻塞作用域、已排除来源和恢复阶段；多个缺口先收敛为一个当前决策点，不逐项打断用户。

**示例话术**：

```text
当前处于准备期。工程中未识别到以下信息，需要你提供：
- 测试环境地址：用于确定请求发送到哪个环境，建议从环境配置或部署说明中确认；
- 测试账号及角色：用于验证鉴权与权限场景，账号本身不要直接发送密码；
- 订单链路定义：用于判断下单后是否需要查单、支付和取消。
```

追问前必须先完成 AI 自助检索和交叉校验：本地/远程 Git 引用、提交对象、源码路由、部署配置、环境变量、已有文档和测试资产均属于优先扫描范围。不得把可由 AI 解决的命名差异、版本映射或配置拼装问题直接转给用户。
仅当目标环境、目标对象、授权边界或不可逆风险无法安全判断时等待用户答复；不得以常见默认值静默填充关键业务信息。

若当前项目存在已确认的项目授权摘要，先自动复用其中仍有效的环境、鉴权、范围和数据规则；只有摘要缺失、指纹漂移、授权越界或清理能力失效时才追问。不得跨项目复用摘要。

**配置判缺前置链（强制）**：针对每个待用值，先检查当前输入，再检查 canonical `docs/test-config.md` / `docs/interface-profile/`，再检查目标环境的 `.panda-api-test-agent/local/secrets/environments/<environment-id>.secret.json`，最后检查活动 Run 已绑定的 RuntimeContext/一次性 bridge 元数据。任一来源已有仍有效值即视为已提供，不得再次询问；只有四处均无可用值时才追问。检查持久 Store 时只确认目标 binding 是否存在和适用，不在交互文本中复述 Secret 值。

### 1.4 请求确认

**触发时机**：准备执行生产/疑似生产、删除或破坏性操作、批量大规模执行、真实外部动作、环境切换、扩大范围或覆盖已有配置时。普通非生产业务写入、日志、轨迹、异步消息和新建测试数据默认不因存在持久化副作用而触发确认。

**交互内容**：用可核对的清单说明测试对象、环境、范围、链路、数据动作和风险，再请求明确确认。

**示例话术**：

```text
我打算这样测：使用测试环境，覆盖正向/异常/边界/鉴权，走“登录 → 下单 → 支付”链路；不删除已有数据，仅使用新建测试数据。确认开始吗？
```

必须确认的场景：

- 生产或疑似生产环境；
- 删除、清理或回滚已有数据；
- 批量、大规模或高频执行；
- 真实外部通知、支付、发货或其他不可逆动作；
- 切换到另一个环境，尤其是接近生产或共享环境前；
- 从核心接口扩大到全量接口、全链路或大规模参数组合前；
- 覆盖或重建已有项目配置前。旧格式不得静默覆盖。

以下动作默认允许：在已确认的非生产环境中创建或修改测试数据、触发业务日志/轨迹/MQ 消息、执行普通失败和成功链路；但必须记录 side_effect、对象引用、数据标签、清理状态和残留风险。

“好的”“继续”“按你说的”仅在上下文中的动作、环境和范围已经完整明确时视为确认；否则继续澄清。

### 1.5 测试设计预览与人工审核

**触发时机**：AI 生成任何拟发送接口请求的测试设计后、发送第一个请求前。需求/功能验证、单接口质量测试、接口调试以及会发送请求的 `PROBE` 均适用。

**强制状态**：设计生成后必须写为 `pending_review` 并停止执行。用户在提出任务时说“直接测”“开始执行”只表示允许生成设计，不等于审核了尚未看到的具体设计。

**先展示设计深度摘要**：列出适用维度、覆盖义务总数、每个维度的义务数、obligation→case 映射、未覆盖/blocked/not_applicable/waived 项、参数组合策略和 Oracle 深度。审核人必须同时看见“已生成什么”和“按事实还缺什么”；不得用维度名称或任意一条用例代替完整性证明。

**每条用例至少展示并纳入审核**：

| 审核项 | 最少内容 |
|---|---|
| 用例 | `case_id`、标题（人类可读的一句话描述，不得用 `case_id` 自身充当标题）、覆盖义务、入口类型、目标/AC 映射、是否拟执行 |
| 场景差异 | 前置业务状态、相对基线请求具体改变了哪个输入、命中哪个业务分支；不得只写“边界/异常”标签 |
| 请求摘要 | 环境、方法、路径、关键参数类别、预计请求次数 |
| 断言 | 状态码、业务 code、关键字段语义、业务规则、正/负副作用和外部 Oracle 摘要；仅字段存在不足以证明核心业务值正确 |
| 数据依赖 | 前置数据、变量来源、账号/角色、前后顺序、清理要求 |
| 副作用 | `read/write/destructive`、影响对象、真实外部动作、数据标签、清理方式和残留风险 |

不得只展示标题级清单后要求整体批准；审核人必须能够看到上述范围。完整请求体与响应样本默认折叠，审核人可按需展开原文。

**编号必须带语义**（两条硬规则）：

- **验收标准编号**（AC01、AC02…）：任何面向用户的输出中，编号首次出现处必须附一句话描述。用例较多时在审核正文头部提供“验收标准速览表”（编号 + 一句话描述 + 本轮覆盖情况），后文可只写编号。只罗列 `AC01–AC19` 而不给描述，等于要求审核人自己去翻 PRD，视为展示不完整。
- **用例标识**（case_id）：清单中每个 `case_id` 必须同行伴随标题。`case_id` 是机器校验用的标识符，不是给人读的标题；`partially_approved` 逐条批准时用户确认的依据是"ID + 标题"的组合。

**审核结果与失效规则**：状态取值、字段别名和“设计变化即重新审核”的判定，统一以 `SKILL.md`「测试设计人工审核门」为准，本节不重复定义。只补充两点展示要求：

- `partially_approved` 必须逐条列出被批准的 `case_id`，其余明确告知保持 `not_run`；不得隐式缩包后冒充整体批准。
- 部分批准后若通过删除未批准用例形成新执行包，新包必须与本次审核范围存在可验证绑定（同一指纹或显式 `supersedes`），不能沿用不匹配的整体指纹。

**审核模板**：

```text
测试设计待审核（pending_review）
入口：<需求/功能验证 | 单接口质量测试 | 接口调试>
目标：<需求、接口或调试问题>
环境：<环境 ID>
设计指纹：<design_fingerprint>

验收标准速览（仅列本轮涉及的）：
- <AC01>：<一句话描述>（本轮：直接验证）
- <AC02>：<一句话描述>（本轮：接口层部分验证）
- <AC13>：<一句话描述>（本轮：不执行，理由 <...>）

用例 1：<case_id> · <标题> · <目标/AC 映射> · 拟执行
- 请求摘要：<METHOD> <路径>；关键参数 <...>；预计 <n> 次
- 断言：<状态码/契约/业务规则/Oracle 摘要>
- 数据依赖：<前置数据/变量/账号角色/顺序/清理>
- 副作用：<read|write|destructive>；对象 <...>；外部动作 <...>；残留风险 <...>

请选择：
A. approved：批准全部列明用例
B. partially_approved：仅批准这些 case_id：<...>
C. rejected：退回修改
D. plan_only：仅保存设计
```

方案审核状态、审核范围、审核指纹和运行门禁必须由 `panda-ai-api-tester-v2` 或可信宿主确定性校验；主 Agent 不自行伪造批准。收到 `approved` 或 `partially_approved` 后，必须先调用 `record_review()` 写回原 Run，并确认 `review_recorded` 成功；此时只进入 feasibility，不得直接执行。若 `executable_case_ids` 非空，再展示执行授权摘要（具体用例 ID+标题、环境、预计请求数、副作用和有效期），通过 `record_execution_authorization()` 写回独立 `execution_approval`；若为 0，则明确“实际请求 0 次”，不得申请授权。`plan_review`、`execution_approval` 与生产/破坏性/批量/真实外部动作的高风险确认相互独立，必须按适用情况全部满足。相同 `run_id + plan_fingerprint + approved_case_ids` 已有有效方案审核时禁止重复展示本节完整模板。若当前 Slice 仅缺高风险授权，只展示风险增量，并明确“原方案审核和执行授权仍有效，本次不是重新审批测试方案或执行范围”。

**执行授权模板**：

```text
执行授权待确认（execution_approval）
环境：<environment_id>
执行范围指纹：<execution_scope_fingerprint>
可执行用例：<case_id + 标题列表>
预计请求：<n> 次
副作用摘要：<read/write/destructive、对象和残留风险>

请选择：
A. approved：授权全部可执行用例
B. partially_approved：仅授权这些 case_id：<...>
C. rejected：本轮不执行
```

显式 `execution_case_ids=[]` 表示零执行，不得回退为全部审核用例；方案审核通过也不得借“继续”“按方案执行”自动补造授权 envelope。

**示例对照**：

正例（每条用例五要素齐全 + 标准决策选项）：

```text
测试设计待审核（pending_review）
入口：需求/功能验证   环境：test3-cps   设计指纹：sha256:c34c…ed37

验收标准速览（本轮涉及）：
- AC01：状态不符校验失败后记录操作日志（类型218，失败）——本轮：直接验证
- AC11：失败日志内容完整（操作人/时间/原因）——本轮：直接验证
- AC04：扫描不存在运单时业务失败且不产生日志/轨迹——本轮：直接验证
- AC13：日志写入失败不阻断主流程——本轮：不执行，故障注入接口层不可验证

用例 3：T03-status-mismatch-failure · 状态不符运单加入包裹失败并记录日志 · AC01/AC11 · 拟执行
- 请求摘要：POST /app/order/resendScan/routeCheckAndSave；关键参数 运单号(状态不符样本)、scanMode=2、taskId；预计 1 次
- 断言：HTTP 200；code≠200；bizErrorCode=97005（原失败返回不变）
- 数据依赖：状态不符测试运单 + 操作账号任务上下文（taskId/角色key）
- 副作用：write；对象=失败日志+内部轨迹（PRD 要求保留）；无清理入口，残留登记

请选择：
A. approved：批准全部列明用例
B. partially_approved：仅批准这些 case_id：T01、T02、T02a、T02b、T04
C. rejected：退回修改
D. plan_only：仅保存设计
```

反例一（禁止——只给编号和 ID，无语义）：

```text
用例 3：T03-status-mismatch-failure · AC01/AC11 · 拟执行
……
本次共 14 条用例，覆盖 AC01–AC19。
```

`AC01/AC11` 是什么验收标准？`T03-status-mismatch-failure` 测的是什么场景？审核人只能去翻 PRD 和猜测，实质上把审核责任转嫁给了用户。`case_id` 不是标题，AC 编号不是描述。

反例二（禁止）：

```text
测试设计如下，共 14 条用例，覆盖 AC01-AC19，没问题我就开始执行了。
```

只有标题级清单，没有请求摘要/断言/副作用，审核人无法实质审核；“没问题我就执行”还把沉默当成了批准。

### 1.6 汇报进度

**触发时机**：子 skill 返回阶段性状态、执行时间较长、出现阻塞、范围发生变化或需要用户决策时。

**连续推进纪律**：设计审批生效后，普通 Slice、已审核 fixture/Oracle/cleanup、安全恢复和 reduce 必须在同一次 Agent 执行中连续推进；Slice 切换只作为内部进度，不得要求用户逐步点击继续。只有设计行为变化、高风险授权、不可推导的运行时输入、不可恢复阻断或终态才向用户返回。`blocked` 必须先解释具体 `failure_class`，不得默认回到测试设计审批。

**交互内容**：报告已经完成、正在进行、阻塞原因和预计下一步，不虚构百分比或执行数量。

**示例话术**：

```text
当前处于执行期，模式为 EXECUTE。panda-ai-api-tester-v2 已形成 12 条结构化用例，正在执行订单下单链路；目前没有清理数据动作。下一次反馈将包含实际执行、通过、失败、错误、跳过和未执行数量。
```

```text
当前处于执行期。执行被测试环境鉴权失败阻塞，已有 8 条用例未执行。我需要你确认测试账号权限或提供可用的安全配置后再继续。
```

### 1.7 呈现结果

**触发时机**：子 skill 完成执行、部分执行、失败或无法继续时。

**交互内容**：给出事实结论、覆盖范围、通过/失败/跳过/未执行数量、关键失败原因、报告位置和下一步建议。

**示例话术**：

```text
执行完成：共 12 条用例，通过 10 条，失败 2 条，跳过 0 条；覆盖下单正向、库存不足异常和鉴权边界。
失败集中在支付回调校验，详细报告位于 `.panda-api-test-agent/reports/order-api-2026-10-29.html`。
下一步可先查看失败请求与响应；如需重试，将先评估重复副作用并生成新的待审核重试设计。
```

若只有用例生成、部分执行、Mock 或跳过，必须明确标注实际状态，不得给出“测试通过”的完整结论。

### 1.8 输出分层与收敛（补充规则）

**触发时机**：任何一次要向用户呈现多个待确认项、缺口、风险或阻塞时。汇报模板只保留在 §4，本节只定义分层字段。

**问题背景**：子 skill 产出的待确认项天然平级、数量多、带内部字段。原样贴出会让用户无法判断优先级，读起来像任务清单堆砌，且不知道下一步该做什么。

**待确认项必须结构化的字段**：

| 字段 | 取值 | 说明 |
|---|---|---|
| `id` | 字符串 | 稳定标识，便于用户回指 |
| `block_stage` | `probe` / `execute` / `promote` / `none` | 阻塞哪个阶段；`none` 表示仅记录备查 |
| `severity` | `hard` / `soft` | `hard` 必须解决才能推进；`soft` 有降级路径 |
| `impact` | 一句话 | 不解决会发生什么，用业务语言 |
| `decider` | 角色 | 产品 / 研发 / 环境负责人 / 用户本人 |
| `unlocks` | 一句话 | 解决后能推进到哪一步 |

**呈现规则**：

1. 正文主区只放 `block_stage` 等于当前或下一阶段、且 `severity=hard` 的项，按阻塞强度排序，最多 3 条。
2. 其余项收进「附录 / 备查」，一句话交代"这些不挡当前推进"。
3. 必须把当前阶段阻塞项收敛成**一个决策点**，用 A/B 选项表达，说明各自代价与产出。
4. 内部字段必须翻译成业务语言；`impact` 不得写成"门禁失败""契约漂移"等技术结论，要写"发不出请求""可能写坏测试数据"这类后果。

**硬标准**：用户读完应能直接回答"现在能不能跑、卡在哪一件事、我该做什么"。若用户需要追问"所以我现在要做什么"，说明本次呈现失败，必须重写而不是补充解释。

**反面样例**（禁止）：

```text
以下问题仍未解除：
1. PRD 仍为 P-HOLD
2. 外发边界冲突
3. 缺少授权摘要
...（连续 9 条平级罗列）
```

该写法没有分层、没有收敛、没有决策点，把判断成本整体推给用户。

**正面样例**（与上述反面样例同源的收敛写法）：

```text
结论：设计已就绪，卡在测试数据一件事上。

当前卡点（不解决则 9 条用例无法执行）：
1. 缺测试运单样本与任务上下文 —— B 组用例只能保持 not_run，
   AC01/AC02/AC10/AC15/AC16 的验收结论无法产生

你现在只需做一个决定：
A. 你直接提供测试环境现成运单号+taskId —— 最快，样本真实性由你保证
B. 用已登记的造数通道（datafactory MCP）在测试环境造数 —— 样本可控，
   作为 fixture 写入任务纳入设计（含 object_ref/teardown/数据标签），
   与其他写用例一并过审核门
C. 改在造数平台支持的其他环境造数 —— 需换环境+新审核

附注（不挡当前推进）：其余 4 条（构造方式、故障注入、部署版本核对等）
属于执行期或其他验证层事项，已登记备查。
```

与反面样例的差异：9 条平级罗列收敛为 1 条阻塞主区 + 1 个 A/B/C 决策点 + 备查一句话；每条阻塞项都写明“不解决会发生什么”。数据类卡点必须先完成数据源前置检查（`data-sources.md` 登记与会话内造数类 MCP）后才允许呈现为缺口，有可用造数通道时以 B 选项形式出现在决策点中，不得漏列。

## 2. 主动追问规则

### 2.1 触发条件

以下情况只产生“待闭合事实”，不得直接触发追问：

- 当前来源未发现测试账号、角色或权限边界；
- 当前来源未发现环境地址、环境变量或部署目标；
- 业务语义、接口依赖、调用顺序、数据准备或断言口径尚未确认；
- 配置存在冲突、过期或暂时不可访问；
- 接口画像缺少 Owner、确认范围、副作用/清理边界，或运行事实与画像不一致。

对上述事实先执行通用证据闭环。只有同时满足以下条件才触发主动追问：

1. 缺失事实确实阻塞完整设计、当前阶段、AC 或用例；
2. 已记录相关来源为 `confirmed/insufficient/conflicted/unavailable/not_applicable`，与当前阻塞直接相关的关键来源不存在未解释的 `not_checked`；
3. 不存在安全、只读、可逆且可能改变当前设计或结论的下一动作；不会改变当前设计或结论的补充动作不得阻塞；
4. 无法进入带明确边界的 `DEGRADED_READY`；完整设计可形成但执行依赖未闭合时应进入该状态而非追问；
5. 已生成 `stop_proof`，包含最小用户输入与恢复阶段。

**前置检查（判数据类追问前强制）**：追问用户提供测试数据之前，必须先完成数据源前置检查——查 `.panda-api-test-agent/data-sources.md` 登记与当前会话可用的造数类 MCP/连接器（如 datafactory），核对支持环境与授权。存在可用造数通道时不得把"缺数据"作为追问抛给用户，改为呈现造数动作设计；确需追问时，追问内容中必须说明已排除的造数路径（evidence），禁止凭"没查过"判缺。

### 2.2 追问格式

采用“缺什么 + 为什么 + 已查什么 + 阻塞范围 + 恢复位置”的格式：

```text
需要你提供：<最小必要信息>。
用途：<该信息影响的阶段、范围或安全边界>。
已完成检查：<已查来源及其 unavailable/insufficient/conflicted 结论>。
是否阻塞：<仅阻塞哪些阶段、AC 或用例；哪些范围仍可继续>。
收到后恢复：<从哪个阶段或动作继续，不重新询问已回答问题>。
```

**示例对照**：

正例：

```text
需要你提供：操作账号在 App 加入包裹页使用的 taskId 和角色 key。
用途：决定加入包裹入口能触发哪个失败分支（无任务/状态不符/非本站），
     直接影响 9 条数据依赖用例的断言取值。
建议来源：App 加入包裹页实际操作记录，或对应角色账号上下文。
是否阻塞：是（仅阻塞数据依赖用例，无数据依赖的 5 条不受影响）。
```

反例（禁止）：只问“给我一些测试数据”——没说用途、没说阻塞范围，用户无法判断给什么、给多少，也无法判断不给会挡住哪些用例。

### 2.3 获取信息后的分类与处理

用户提供配置后必须逐项分类并按下表路由，不得先一律当作临时运行输入：

| 分类 | 判定 | 去向 |
|---|---|---|
| `stable_non_secret` | 稳定、可跨 Run 复用且不敏感，例如环境 ID、稳定 Base URL、超时、接口路由/Schema | 转交 L1 写入 canonical `docs/test-config.md` 或 `docs/interface-profile/`；主 Agent 不直接写 |
| `persistent_secret` | 用户明确要求保存、或该环境长期复用的 Secret | `.panda-api-test-agent/local/secrets/environments/<environment-id>.secret.json`，按 environment ID + binding key 精确存取 |
| `ephemeral_secret` | 仅本次/短期有效的 Token、Cookie、密码或签名材料 | 活动 Run 的宿主内存；确需落盘时仅用 `.panda-api-test-agent/local/runtime/secrets/{run_id}.secret.json` 一次性 bridge |
| `runtime_non_secret` | 仅本次运行使用的非敏感值，例如临时 URL、请求变量、临时对象 ID | 活动 Run/RuntimeContext，不写 canonical config |
| `requirement_fact` | PRD、AC、业务语义、范围、基线或验收口径 | `.panda-api-test-agent/requirements/<requirement-id>/context.json` |

- 分类后记录 key、environment ID、目标 binding、来源与分类，不复制 Secret 值到分类记录、对话摘要、canonical config、接口画像、TestPackage 或需求 context。
- 用户未明确 Secret 是否需要长期保存时，按有效期和表达判断；无法判断且会影响落盘时，只追问“持久保存还是仅本次使用”这一项，不要求用户重复提供值。
- 已成功写入 persistent Store、canonical config、需求 context 或活动 Run 的值，后续只引用其 key/binding 和来源；不得重复索要。写入失败时报告写入失败，不得把失败伪装成仍缺用户输入。
- 用户信息不足时先由 AI 按“当前输入 → canonical config/画像 → 持久 Secret Store → 活动 Run”检索、解析和交叉验证，不用猜测值替代；只有全部来源均无可用值时才继续追问。
- 用户提出“再试一次”“重跑”时，不得自动复用上次请求执行。先保留首次事实，将重试作为新的具体动作，说明重复写入/幂等风险并重新进入 `pending_review`；写请求结果未知时默认不重试。
- 用户提供的分支/版本号异常时，先尝试匹配远程 ref、Tag、Commit、相近命名和隔离 worktree，并记录实际采用的基线及证据。
- 对画像或项目适配问题按事实类型追问正确责任人：接口契约与代码副作用找研发负责人，纯业务语义找产品/业务负责人，测试充分性和 Oracle 找测试负责人；确认结果和适配规则交由 L1 写入 `.panda-api-test-agent/adapter/` 或接口画像，主 Agent 不直接修改。
- 用户明确无法提供时，说明受影响的覆盖范围，并将相关项标记为未执行或待确认。
- 不允许为了推进流程而把未知项写成默认账号、默认环境或默认业务规则。

### 2.4 外部验证层证据的追问与登记

`partial`/`none` 的 AC 在接口层之外还需要 UI、DB、MQ、审计或人工验收时，按 2.2 的格式追问“差哪一层、要什么形式的证据”，并明确不提供时的后果（该 AC 保持 `inconclusive`）。

```text
还需要你提供：AC02 在测试环境页面上的订单详情截图（含订单号）。
用途：该 AC 判定为 partial，接口层只能证明订单已创建，“页面展示正确”只能由 UI 层证明。
建议来源：测试环境页面操作，或客户端同学的验收记录。
是否阻塞：是（缺此证据 AC02 保持 inconclusive，需求无法整体判通过）。
```

收到后必须经 `scripts/external_evidence.py::record_external_evidence` 登记（`ac_id`、`layer`、`status`、`refs`、`provided_by`），再调用 `refresh_requirement_report` 重算，不允许只在对话里确认、只改内存结论，或把用户口头描述直接写成 `passed`。

追问纪律：

- 不给证据形式建议就让用户“自己看着办”属于无效追问。
- 用户说“我看过了没问题”但没有可引用凭证时，如实登记为 `blocked` 或继续索要凭证，不得写成 `passed`。
- 用户明确表示不打算验证某一层时，登记 `blocked` 并说明原因，报告中体现为缺口，不得隐去。

## 3. 请求确认规则

### 3.1 确认前必须说明

请求确认前，至少说明：

- 测试环境。
- 测试对象和业务链路。
- 覆盖范围。
- 数据准备、清理或回滚动作。
- 是否会覆盖已有配置。
- 用户确认后将调度哪个子 skill。

### 3.2 标准确认话术

```text
我打算这样测：<环境>，覆盖<范围>，走<链路>；普通非生产测试写入、日志、轨迹和异步消息按默认策略执行，<删除/批量/外部/生产动作>将<请求确认或不执行>；执行模式为 <PROBE/EXECUTE>，默认不生成 pytest。
确认后将调度 panda-ai-api-tester-v2 生成结构化 TestPackage 并执行。<若无高风险动作，直接开始；若存在高风险动作，再请求确认。>
```

### 3.3 未确认时的纪律

- 测试设计未获 `approved` 或 `partially_approved` 时，任何入口都不得发送接口请求；普通非生产副作用默认允许策略只在设计审核通过后生效（审核规则见 `SKILL.md`「测试设计人工审核门」）。
- 设计已审核但高风险动作未确认时，可继续本地静态检查和不包含该高风险动作的已审核用例；不得把高风险动作默认为已确认，也不得再次展示完整测试设计。高风险确认必须标注为独立授权，并声明 `design_review_still_valid=true`。
- 用户只确认了环境，不代表确认了测试设计、数据清理或全量覆盖；各门禁独立有效。
- Token、连接或运行时绑定值缺失只暂停原 Run；补齐或轮换同一 binding 的 Secret 值后，在相同环境拓扑、URL、binding、指纹和范围下免重新审核继续。环境拓扑、URL 或 binding 变化仍按原规则生成新设计并重审。内部 Slice、执行游标、事件账本、资源状态或报告变化不构成新设计。

## 4. 用户反馈规范

每次调度后必须告知：

1. 当前处于哪个阶段。
2. 刚调用了哪个 skill。
3. 调度结果或当前进度。
4. 下一步是什么，或者需要用户做什么。

### 准备期反馈模板

禁止使用"待确认项：<逐项列出>"这类平铺写法。必须按下述三段式收敛：

```text
结论：<一句话——配置是否就绪、当前卡在哪>

当前卡点（只列阻塞本阶段且必须解决的，最多 3 条）：
1. <卡点> —— <不解决的后果>

你现在只需做一个决定：
A. <选项> —— 代价 <...>，产出 <...>
B. <选项> —— 代价 <...>，产出 <...>

附注（不挡当前推进）：<其余 N 项的性质，例如"样本矩阵、查询链路等属于执行期前置，配置阶段不需要" >
```

准备期若阻塞项为 0，直接写"配置已就绪，可以进入执行期"，不要为了完整而罗列备查项。

### 执行期反馈模板

```text
结论：<能不能跑、跑出了什么、卡在哪>

当前卡点（仅门禁失败或必需用例未执行时出现，最多 3 条）：
1. <卡点> —— <不解决的后果>

你现在只需做一个决定：
A. <选项> —— 代价 <...>，产出 <...>
B. <选项> —— 代价 <...>，产出 <...>

结果：实际请求 <n> 次；通过 <n> / 失败 <n> / 错误 <n> / 跳过 <n> / 未执行 <n>。
报告：<结构化 TestResult 生成的报告位置；没有则明确说明尚未生成>
```

门禁失败时，"结果"行必须同时写明业务用例全部 `not_run` 和发送请求数，避免用户误以为测试已经跑过。

**示例对照**：

正例（执行期，门禁失败场景）：

```text
结论：现在不能跑。门禁在鉴权一步失败，业务请求一次都没发。

当前卡点：
1. Bearer Token 已过期（401） —— 强行继续只会让 14 条用例全部 not_run

你现在只需做一个决定：
A. 提供新 Token —— 1 分钟，恢复执行
B. 暂停本轮 —— 已批准范围保留，Token 就绪后免重新审核继续

结果：实际请求 1 次（仅鉴权门禁请求，不计入业务用例）；通过 0 / 失败 0 /
     错误 0 / 跳过 0 / 未执行 14。
报告：尚未生成（无业务执行）。
```

反例（禁止）：

```text
执行受阻，环境鉴权失败。
```

没写"0 次业务请求、14 条 not_run"，用户很容易误读成"测过了但有环境问题"；也没给下一步选项，用户必须追问才知道该做什么。

## 5. 交互边界与安全

- 主 Agent 是唯一面对用户的一层；子 skill 的内部过程应被转译为清晰的用户反馈。项目适配层由 L1 初始化和维护，主 Agent 不直接创建、修改或补写适配器内容。
- 不向用户承诺子 skill 尚未返回的结果。
- 不把配置生成成功表述为测试成功。
- 不把调度成功表述为执行成功。
- 不把 pytest 文件生成、语法检查或 collect 成功表述为业务通过。
- 用户未明确提出 pytest/CI 时，不主动建议把每次即时验证都固化为 pytest。
- 不展示明文密码、令牌、密钥或完整敏感账号信息。凭据的落盘与传递以 `SKILL.md`「凭据与运行值」为准：持久 Secret Store 与一次性 Run bridge 并存，本节不改变既有凭据展示、运行证据原样记录或报告策略。
- 禁止自动重试。任何重试都必须保留首次结果、评估幂等和重复副作用，并作为设计变化重新审核。
- 对生产环境、共享环境、数据删除和大规模执行保持保守：信息不足时暂停并追问或请求确认。
- 用户提出无 teardown 写入时，必须明确说明这是结构化 cleanup waiver 例外而非静默跳过；逐项确认 waiver_id、原因、残余风险、审批者、有效期、标签和残留对象。生产、destructive、write_attempt、批量和 PROMOTE 永不放行；结果不得称完整通过。
